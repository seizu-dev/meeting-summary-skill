# tl;dv のローカル録音ファイルに関する実測知見

[tl;dv](https://tldv.io/) は会議レコーダー。無料プランでは自動文字起こしが使えないが、**クライアントはローカルに録音ファイルを残す**ため、それを [../SKILL.md](../SKILL.md) の手順に流し込める。

以下は 2026-09-06 および 2026-09-13 に Windows 版クライアントで実機検証した内容。他の録音ツールを使う場合は読み飛ばしてよい。

## ファイルの所在と命名規約

| 項目 | 内容 |
| --- | --- |
| 録音フォルダ | ユーザーホーム直下の `.tldv`（Git Bash なら `$HOME/.tldv`） |
| ファイル名 | `YYYY-M-D-Meeting(Audio)-YYYY-MM-DDTHH-MM-SS-mmmZ.webm` |
| 先頭の `YYYY-M-D` | **ローカル日付**（ゼロ埋めなし）。素早い絞り込みに使える |
| 末尾の ISO タイムスタンプ | **録音開始時刻・UTC**。ローカル時刻へはオフセットを加算する |
| ファイル更新日時（mtime） | 録音**終了**時刻とほぼ一致。長さの裏取りに使える |
| 実際の中身 | 拡張子は `.webm` だが**中身は MP4 コンテナ + Opus 音声**（48kHz / 2ch）。拡張子が実態と一致していない |

ホームディレクトリのパスは PC ごとに変わるため、絶対パスを直書きせず `$HOME/.tldv` で参照すること。

## 候補の一覧表示（参考）

**通常は [../SKILL.md](../SKILL.md) の Step 1 にある汎用スニペットを使えばよい。** tl;dv の `.webm` は中身が MP4 コンテナなので `creation_time` タグを持っており（実測 `2026-09-11T05:00:59Z`、ファイル名のタイムスタンプと1秒差で一致）、ファイル名をパースしなくても録音開始時刻が取れる。

以下はファイル名からも同じ値が取れるという参考。**タイムゾーン変換は必ずこの epoch 方式を使う**（理由は [../SKILL.md](../SKILL.md) の「タイムゾーン変換の注意」を参照）。

```bash
for f in "$HOME/.tldv/"*.webm; do
  [ -e "$f" ] || continue
  b=$(basename "$f")
  ts=$(echo "$b" | sed -n 's/.*-\([0-9]\{4\}-[0-9]\{2\}-[0-9]\{2\}\)T\([0-9]\{2\}\)-\([0-9]\{2\}\)-\([0-9]\{2\}\)-[0-9]*Z\.webm$/\1 \2:\3:\4/p')
  ep=$(date -u -d "$ts UTC" +%s)
  jst=$(date -u -d "@$((ep + 32400))" '+%Y-%m-%d %H:%M')
  dur=$(ffprobe -v error -show_entries format=duration -of csv=p=0 "$f" 2>/dev/null)
  min=$(awk -v d="$dur" 'BEGIN{printf "%.0f", d/60}')
  printf '開始JST %s | %3s分 | %s\n' "$jst" "$min" "$b"
done
```

ここで表示される長さはタイムライン長（`format=duration`）。会議の予定時刻・予定時間と突き合わせて候補を絞る用途にはこちらが適切。

## 約1秒周期の音声欠落（重要）

tl;dv の録音ファイルでは、**プレーヤーが表示する長さと `ffprobe` の `format=duration` が食い違う。**

実音声で約54分の録音での実測例:

| 指標 | 値 |
| --- | --- |
| 実音声の長さ（パケット `duration_time` の総和） | 3,226.99秒（53分46.99秒） |
| タイムラインの長さ（`format=duration`） | 3,355.82秒（55分55.82秒） |
| 差 | 128.82秒 |

### 原因

**約1.02秒ごとに、約39msの音声が欠落している。**

- 通常のパケットは約59ms。しかし一定周期で **21msの短いパケット**が現れ、その直後に必ず約39msの空白が続く（実測で3,289件、例外なく100%が短パケットの直後）
- 短パケットの出現間隔は 1.017〜1.022秒（平均1.020秒）と極めて規則的。ランダムな不調ではなく、tl;dv 録音側の約1秒周期のバッファ境界での取りこぼしとみられる
- 欠落量は音声全体の約3.8%
- **この欠落は tl;dv 固有。** 同じ方法で Windows サウンドレコーダーの録音を測ると差は0.00%だった（[windows-sound-recorder.md](windows-sound-recorder.md)）

### 実務上の注意

- **ユーザーに録音長を伝えるときは実音声の長さを使う。** `format=duration` をそのまま「録音は◯分」と報告するとプレーヤー表示と食い違う
- 変換後の mp3 は**タイムライン長**になる。ffmpeg が欠落箇所に無音を埋めるため、39msの無音が数千個散らばった状態で出力される。処理上の問題はない
- 39msは日本語の子音〜短い音節が1つ消える長さ。**文字起こしの固有名詞誤変換が多いことの一因である可能性がある**（仮説。因果は未検証）

## その他の実測事項

| 項目 | 結果 |
| --- | --- |
| 元ファイル（`.webm`）の直接アップロード | **HTTP 400 で拒否される**（検証済み）。ffmpeg 変換は必須 |
| Gemini Notebook MCP（claude.ai コネクタ）の接続形態 | **リモート接続**。`source_add(path=...)` はアップロードせず `upload_required` を返す |
| Gemini Notebook アカウント上限 | notebook 100件 / source 50件 |

## 処理時間のベンチマーク

見積もりの参考値。ユーザーに待ち時間を伝えるときに使う。

| 録音長（タイムライン／実音声） | 元ファイル | mp3変換 | 変換後 | アップロード | Gemini Notebook処理 | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 36分 ／ 実音声は未計測 | 34.9MB | 約6秒 | 17.2MB | 約9秒 | 約80秒 | 約95秒 |
| 55分56秒 ／ 実音声 53分47秒 | 54.4MB | 9.4秒 | 26.8MB | 9.2秒 | 40〜70秒（推定） | 約60〜90秒 |

- **変換は音声長にほぼ比例する。** mp3 は元ファイルの約半分のサイズになる
- アップロードは実測で平均 3.05MB/s。26.8MB で 8.8秒（転送のみ）
- 54分の録音の Gemini Notebook 処理時間は幅がある。「curl 完了 → `source_wait` が ready 返却 → 直後にタイムスタンプ取得」で 69.6秒だったが、**この区間にはエージェントのターン往復が2回含まれる**（同条件での1往復の実測は 20.3秒）。サーバー側で完結する計測手段がないため切り分けできず、推定値にとどまる
- ユーザーに伝えるときは「変換とアップロードで20秒前後、処理待ちで1〜2分」程度の粒度でよい
